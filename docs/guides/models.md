# Models and queries

A model is one database table. Its attributes come from the table's columns;
what you declare is everything else: relationships to other models,
validations, lifecycle hooks and reusable query scopes. Models are also how
you read and write records yourself — in a custom action, a hook or a seed
file.

This guide uses the blog from [Getting started](getting-started.md) and
examples from
[examples/social-network](../../examples/social-network/app/models/).

## The model file

```javascript
// app/models/user.js
import { Model } from 'lumen-framework';

class User extends Model {
  static hasMany = {
    posts: {
      inverse: 'user'
    }
  };
}

export default User;
```

- **The table** is the pluralized, underscored model name: `User` → `users`,
  `BlogPost` → `blog_posts`. Set `static tableName` to use another.
- **The attributes** are the table's columns, camelCased: a `created_at`
  column is `user.createdAt`. Nothing needs declaring; a migration adding a
  column adds the attribute.
- **The primary key** is `id`; set `static primaryKey` for another column.
  Ids are generated by the database.
- **Timestamps:** `createdAt` and `updatedAt` are set on create and update
  when the table has them (`table.timestamps()` in a migration).

## Relationships

Every relationship names its **`inverse`** — the relationship on the other
model that points back:

```javascript
class Post extends Model {
  static belongsTo = {
    user: { inverse: 'posts' }       // posts.user_id → users.id
  };

  static hasOne = {
    image: { inverse: 'post' }       // images.post_id → posts.id
  };

  static hasMany = {
    comments: { inverse: 'post' },   // comments.post_id → posts.id
    tags: {                          // through categorizations
      inverse: 'posts',
      through: 'categorization'
    }
  };
}
```

| Kind | Foreign key lives on | Value |
|---|---|---|
| `belongsTo` | this table (`user_id`) | One record or `null` |
| `hasOne` | the other table (`post_id`) | One record or `null` |
| `hasMany` | the other table, or a join model with `through` | An array |

Options beside `inverse`:

- **`model`** — the related model when it differs from the relationship's
  name: `author: { inverse: 'books', model: 'user' }`.
- **`foreignKey`** — the column when it isn't `<name>_id`.
- **`through`** — the join model of a many-to-many relationship. The join
  model (`Categorization`) `belongsTo` both sides.

### Reading and assigning

A relationship reads as a promise; it is loaded on first use and then kept on
the record:

```javascript
const post = await Post.find(1);
const author = await post.user;
const comments = await post.comments;
```

A `belongsTo` can be set by record or by its foreign key, on create or later:

```javascript
await Post.create({ title: 'Hello', body: '…', user: ada });
await Post.create({ title: 'Hello', body: '…', userId: ada.id });

post.user = ada;
await post.save();
```

To load relationships with the records instead of one query per record, use
`include` (see [Queries](#queries)).

## Validations

`static validates` maps attributes to functions that return whether a value
is valid. They run before every create and update:

```javascript
class User extends Model {
  static validates = {
    email: value => typeof value === 'string' && value.includes('@')
  };
}
```

A failing validation throws a `ValidationError`. Through the API, that is a
`422 Unprocessable Entity` pointing at the attribute:

```json
{
  "errors": [
    {
      "status": "422",
      "title": "Unprocessable Entity",
      "source": { "pointer": "/data/attributes/email" },
      "detail": "Validation failed for email."
    }
  ],
  "jsonapi": { "version": "1.0" }
}
```

Lumen ships no validator library; use your own functions or a package like
[validator](https://www.npmjs.com/package/validator).

## Hooks

`static hooks` runs functions at points of a record's life. They run in this
order:

| Creating | Updating | Deleting |
|---|---|---|
| `beforeValidation` | `beforeValidation` | `beforeDestroy` |
| `afterValidation` | `afterValidation` | `afterDestroy` |
| `beforeCreate` | `beforeUpdate` | |
| `beforeSave` | `beforeSave` | |
| `afterCreate` | `afterUpdate` | |
| `afterSave` | `afterSave` | |

A hook receives the record and the write's **transaction**, `(record, trx)`.
Everything it does through the record — reading a relationship, `update`,
`save`, `reload` — runs in that transaction, and so does anything it does
through `Model.transacting(trx)`. If the write fails, all of it is rolled
back:

```javascript
class User extends Model {
  static hooks = {
    async beforeSave(user) {
      if (user.isNew || user.dirtyAttributes.has('password')) {
        user.password = await hashPassword(user.password);
      }
    }
  };
}

class Comment extends Model {
  static hooks = {
    async afterCreate(comment, trx) {
      const post = await comment.post; // in the transaction

      await Notification.transacting(trx).create({
        recipientId: post.userId,
        message: 'Someone commented on your post'
      });
    }
  };
}
```

Use `trx` for every query on *other* models in a hook. A query without it
runs on another connection: it cannot see what the write has done yet, and
with a single connection (SQLite's default) it waits for the transaction
forever.

Inside a hook, the record is a proxy of the instance being written: attributes
read and assign as usual, but compare records by `getPrimaryKey()`, not `===`.

## Creating, updating and deleting

| Call | Does |
|---|---|
| `Model.create(props)` | Inserts a record and resolves with it. |
| `record.update(props)` | Sets `props` and saves. Resolves with the record; `didPersist` is `false` when nothing changed. |
| `record.save()` | Saves the changes made by assigning attributes. |
| `record.destroy()` | Deletes the record. |
| `record.reload()` | Fetches the record again. |
| `record.rollback()` | Discards unsaved changes. |

A record tracks its changes: `record.isDirty`, and `record.dirtyAttributes`
(a `Map` of the changed attributes).

Each write runs in a transaction of its own, with its hooks, unless you pass
one (see [Transactions](#transactions)).

## Queries

The query methods start on the model and chain. A query runs when it is
awaited (or returned from a controller action, which awaits it):

```javascript
const posts = await Post.where({ isPublic: true })
  .order('createdAt', 'DESC')
  .include('user')
  .limit(10)
  .page(2);
```

| Method | Example | Result |
|---|---|---|
| `find(id)` | `User.find(1)` | The record; **throws** `RecordNotFoundError` (a `404` through the API) if there is none. |
| `first()`, `last()` | `User.where({ name }).first()` | The first or last record by primary key (or by `order`), or `undefined`. |
| `all()` | `User.all()` | Every record. |
| `where(conditions)` | `User.where({ name: ['Bob', 'Cy'] })` | Records matching every condition; an array means *any of*. |
| `not(conditions)` | `User.not({ name: 'Bob' })` | The opposite of `where`. |
| `whereBetween(conditions)` | `Post.whereBetween({ id: [1, 10] })` | Values within a range, inclusive. |
| `whereRaw(sql, bindings)` | `Post.whereRaw('title LIKE ?', ['T%'])` | A raw SQL condition, with bound values. |
| `order(attribute, direction)` | `User.order('name', 'DESC')` | Sorted; `'ASC'` by default. |
| `limit(n)`, `offset(n)`, `page(n)` | `User.limit(10).page(2)` | Records 11–20. |
| `select(...attributes)` | `User.select('name')` | Only those columns. |
| `distinct(...attributes)` | `User.distinct('name')` | Unique values. |
| `include(...relationships)` | `User.include('posts')` | Loads the relationships with the records, one query per relationship. |
| `count()` | `User.where({ name }).count()` | The number of matching records. |

Attributes are camelCase in conditions (`{ userId: 1 }`), as on records.

### Scopes

A scope is a named, reusable piece of a query. Declare it in `static scopes`
— `this` is a query of the model — and it becomes a method that chains like
the built-in ones:

```javascript
class Post extends Model {
  static scopes = {
    isPublic() {
      return this.where({ isPublic: true });
    },

    byUser(user) {
      return this.where({ userId: user.id });
    }
  };
}
```

```javascript
await Post.byUser(ada).isPublic().order('createdAt', 'DESC');
```

`unscope('isPublic')` removes a scope from a query again. A scope narrows the
queries that call it; to keep records from every request, use it in a
[visibility rule](controllers.md#visibility-rules) instead.

## Transactions

Every write runs in a transaction: the record, its hooks, and what they do
with the transaction commit or roll back together. To group several writes,
start one yourself with `Model.transaction`, and pass it on with
`transacting`:

```javascript
await Post.transaction(async trx => {
  const post = await Post.transacting(trx).create({ title: 'Hello', body: '…' });

  await Tag.transacting(trx).create({ name: 'news' });
  await post.transacting(trx).update({ isPublic: true });
});
```

If the function throws, everything in it is rolled back.

- **`Model.transacting(trx)`** — its `create` and every query it starts
  (`find`, `where`, `first`, scopes, …) run in `trx`, including the queries
  that load `include`d relationships.
- **`record.transacting(trx)`** — its `save`, `update`, `destroy`, `reload`
  and relationship reads run in `trx`.
- **`query.transacting(trx)`** — for a query built another way.

Reads in a transaction see what it has written so far; reads outside it see
only committed data.

## Errors from the database

Write errors reach the API as JSON:API errors:

| Error | Response |
|---|---|
| `ValidationError` (a failing `validates`) | `422 Unprocessable Entity`, pointing at the attribute |
| A unique constraint violation | `409 Conflict` |
| `RecordNotFoundError` (`find`) | `404 Not Found` |

```json
{
  "errors": [
    {
      "status": "409",
      "title": "Conflict",
      "detail": "SQLITE_CONSTRAINT: UNIQUE constraint failed: users.email"
    }
  ],
  "jsonapi": { "version": "1.0" }
}
```
